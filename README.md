# Техническое описание программного комплекса «Diplom_CRM»

Данный репозиторий содержит дипломный проект по разработке веб-ориентированной CRM-системы, предназначенной для автоматизации бизнес-процессов коммерческих отделов, контроля воронки продаж и сквозного мониторинга активности менеджеров.

В основе решения лежит архитектурный паттерн MVC с гибридным подходом к UI: рендеринг на стороне сервера (SSR) совмещен с реактивными компонентами на стороне клиента без использования ресурсоемких SPA-фреймворков.

---

## 1. Архитектура базы данных и ORM-слой

Взаимодействие с СУБД PostgreSQL реализовано через объектно-реляционный маппер **Entity Framework Core 10**. Информационная модель включает 5 основных наборов данных (DbSet).

### Подсистема безопасности и кастомный профиль пользователя
Аутентификация и разграничение прав (роли Admin и Manager) построены на базе **ASP.NET Core Identity**. Стандартный класс `IdentityUser` расширен до доменной модели `AppUser`, в которую внедрены следующие бизнес-поля:
* `FirstName` (string) — имя сотрудника.
* `LastName` (string) — фамилия сотрудника.
* `Deals` (ICollection) — коллекция связанных сделок (связь «один-ко-многим»).
* `Companies` (ICollection) — коллекция закрепленных контрагентов.

### Структура бизнес-сущностей (DbSet)
* `Companies` — реестр контрагентов, жестко привязанных к ответственному менеджеру через `AppUserId`.
* `Contacts` — контактные лица клиентов, находящиеся в отношении «многие-к-одному» с таблицей `Companies`.
* `Deals` — коммерческие сделки, содержащие финансовые показатели и привязку к этапам воронки.
* `Activities` — сквозной лог коммуникаций (звонки, задачи, email). Выступает связующим звеном между сущностями `AppUser`, `Companies` и `Deals`.

## 2. Жизненный цикл сделки и логика Канбан-доски

Состояние коммерческого процесса в системе детерминировано четырьмя фиксированными статусами. Валидация переходов между ними контролируется на уровне бизнес-логики бэкенда:

1. `new` — первичная регистрация лида в системе.
2. `in progress` — стадия активной проработки (переговоры, подбор оборудования, ТКП).
3. `won` — финальный положительный статус (договор подписан, сделка выиграна).
4. `lost` — финальный отрицательный статус (отказ клиента, сделка сорвана).

### Механизм синхронизации данных:
При перемещении карточки сделки на фронтенде с помощью библиотеки `Sortable.js`, клиент генерирует асинхронный `POST`-запрос средствами `htmx`. Бэкенд принимает идентификаторы сделки и целевой стадии, выполняет транзакцию в PostgreSQL и возвращает изолированный HTML-фрагмент (Partial View) для динамического пересчета суммарных показателей колонок воронки без перезагрузки страницы.

## 3. Технологический стек фронтенда и клиентские библиотеки

Для обеспечения высокой отзывчивости интерфейса и аналитического функционала интегрирован следующий пул библиотек:

* **Bootstrap 5 & Bootstrap Icons** — каркас адаптивной верстки, сетка UI и системная графика.
* **htmx** — декларативное управление AJAX-запросами непосредственно из HTML-атрибутов (фильтрация, реактивное закрытие задач).
* **jQuery** — обработка клиентских триггеров (включая динамическую разблокировку связанных селекторов Сделок/Менеджеров после выбора Компании).
* **Chart.js** — визуализация аналитических данных Дашборда (Win Rate, объем воронки) на базе HTML5 Canvas.

## 4. Развертывание и первичная инициализация

1. **Миграция БД:** Развертывание схемы данных и системных таблиц Identity в PostgreSQL выполняется командой:
   `dotnet ef database update`
2. **Сидирование (Data Seeding):** При первом запуске бэкенд автоматически проверяет наличие учетных записей и генерирует роли `Admin`, `Manager`, а также создает корневой аккаунт администратора для первичного входа в систему.
